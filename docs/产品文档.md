# dsh-macos-notify 产品文档

> 平台：macOS 桌面端 / `dsh web` 浏览器 · 状态：交互通知与完成通知均已通过真机验证（2026-11-24，DSH 0.2.3-alpha.2）
>
> 定位：README 面向「装好就能用」的使用者；本文面向产品、测试与维护。改行为时先更新本文规格，再改代码与烟测断言。

---

## 0. 一页纸摘要

| 项目 | 内容 |
|---|---|
| 一句话定位 | 把 DSH 里「等你响应」的阻塞交互与「一轮跑完」的完成事件，镜像为 macOS 系统通知。 |
| 覆盖事件 | 授权（`approval`）、提问（`question`）、计划审批（`plan-review`）、未来任何待处理交互的通用兜底，以及会话从运行转为空闲的完成事件（`running: true → false`）。 |
| 明确不做 | 不改交互决策、不拦 waterfall、不提供通知内快捷按钮、不做声音或免打扰策略、不做非 macOS 的专门适配、不保留完成历史。 |
| 最大限制 | 通知由渲染进程发出：页面关闭时没有通知；基于 Web Notification，而非原生通知 API。 |

---

## 1. 背景与目标

### 1.1 三个缺口

DSH 的阻塞交互——授权、提问、计划审批——都以对话内面板呈现，但「需要响应」这件事被锁在窗口里：

1. **窗口不在前台**：切到别的 App 或最小化后，面板不可见，agent 一直停在那里等。
2. **请求属于别的会话**：多会话并行时，你眼前的会话没有异常，另一个会话的请求可能已经等了很久。
3. **任务跑完不知道**：agent 在后台跑完一轮后只是安静空闲下来；窗口不在前台，你不会知道现在可以回来查看结果。

系统通知是唯一跨应用可见的提醒通道；而 macOS 上真正「属于 DSH」的通知，应该由 DSH 自己发出，而不是借助终端或脚本进程。

### 1.2 产品目标

- **不遗漏**：订阅 `sessionStatus` 快照，覆盖全部 `kind` 与 `running` 边沿，未知领域走通用兜底。
- **不打扰**：前台且正看着事件所属会话时静默；完成时带着阻塞交互只弹交互通知。
- **可定位**：点击切回会话；提问 / 计划审批重开作答面板。
- **无副作用**：只读观察发布面，不消费、不重排、不改写决策；所有外部调用失败都静默降级。

---

## 2. 用户场景

1. **后台跑任务**：切去看日志，agent 请求写入工作区外文件 → 系统通知，点击回来点「允许」。
2. **多会话**：正在改前端，另一个会话的提问已经等了 3 分钟 → 通知里直接写会话名。
3. **计划审批**：提交方案后去倒咖啡 → 通知显示 `计划：<方案标题>`，回来批准。
4. **等任务跑完**：让 agent 跑一个长任务后切去写文档 → 完成通知弹出，点击回来看结果；如果跑完时它还要提问，则只弹提问通知。

## 3. 功能规格

### 3.1 交互覆盖矩阵

插件按 `pendingInteraction.kind` 分发，不针对某一种交互写特判：

| `kind` | 典型来源 | 标题 | 正文（第一行） | 点击行为 |
|---|---|---|---|---|
| `approval` | 工具申请越权执行 | `DSH 等待你的授权` | `工具：原因`；无原因时 `工具 请求越权执行` | 切到会话，不额外重开面板 |
| `question` | `ask_user_question` 提问 | `DSH 等待你的回答` | 第一个问题的原文；多个问题时追加 `（共 N 个问题）` | 切到会话 + 重开作答面板 |
| `plan-review` | 计划模式提交方案 | `DSH 等待你审批计划` | `计划：<方案标题>`；取不到标题时退回问题原文 | 切到会话 + 重开作答面板 |
| 其他（未来新增） | 任何注册到待处理交互的领域 | `DSH 等待你的响应` | `有操作需要你处理` | 切到会话 |

正文第二行统一为 `会话：<会话标题>`；会话标题暂不可用时省略该行。

### 3.2 完成通知

会话的 `running` 从 `true` 变成 `false`，表示一轮工作已经结束、agent 空闲下来。插件把这个边沿投影成一条完成通知：

| 事件 | 触发条件 | 标题 | 正文（第一行） | 点击行为 |
|---|---|---|---|---|
| 会话完成 | `running` 由 `true` 变 `false`，且结束时没有阻塞交互 | `DSH 会话已完成` | `本轮已结束，点击查看结果` | 切到会话，不重开面板 |

补充规则：

- **只认真实边沿**：必须先在快照里观测到 `running === true`，之后观测到 `running === false`；启动时本来就空闲的会话不补弹，`undefined` 中间态不算完成。
- **交互优先**：同一快照里还有未结算的 `pendingInteraction` 时，说明这次停下是在等用户，不弹完成通知。
- **不报子会话**：`origin === 'subagent'` 的会话完成时不弹；等主会话自己结束时再提醒。

### 3.3 判定流程

交互通知按顺序检查，任一步不通过就不创建通知：

1. **数据在**：`uiSession.sessionStatus` 快照中该会话有 `pendingInteraction`。
2. **未结算**：不存在 `review`（只读「查看回答」回放卡片），且 `answerable !== false`。
3. **可索引**：`pendingInteraction.key` 是字符串。

完成通知按顺序检查：

1. **有新边沿**：该会话上一次观测为 `running === true`，本次为 `running === false`。
2. **没有阻塞交互**：快照中没有未结算的 `pendingInteraction`（`review` 卡片与 `answerable === false` 不算阻塞）。
3. **不是子会话**：目录里 `origin !== 'subagent'`。

两者共用的最后三步：**能发**（`Notification` 是构造函数且权限为 `granted`）→ **该提醒**（通过安静规则，见 3.6）→ **构造成功**（`new Notification(title, { body, tag })` 不抛错）。

### 3.4 静默、去重与关闭

交互通知：

- **同一请求只一条**：活动通知按 `pending.key` 存在内存 Map 中，已存在的 key 不重复创建。
- **系统层合并**：`tag` 为 `dsh-macos-notify:<sessionId>:<pending.key>`；tag 相同的通知由 macOS 合并，不同请求互不覆盖。
- **已结算不提醒**：`review` 卡片与 `answerable === false` 的授权既不创建通知，也会让同 key 的残留通知关闭。
- **请求消失即关闭**：每次快照变化后，不在当前待处理集合里的活动通知都会被 `close()`。

完成通知：

- **每个会话只保留最新一条**：按 `sessionId` 存在独立 Map 中；再次完成先关闭旧通知再创建新的。
- **开始新一轮即关闭**：观测到 `running === true` 时关闭该会话的完成通知。
- **会话离开投影即关闭**：会话被归档、删除或从快照中消失时关闭。
- **系统层合并**：`tag` 为 `dsh-macos-notify:session-complete:<sessionId>`，与交互通知的 tag 空间分开。

两者共同：插件下线（禁用、卸载、热重载）时退订 `sessionStatus` 并关闭全部活动通知。

### 3.5 点击行为

点击通知按以下顺序执行，每一步失败都不影响后续可用部分：

1. `window.focus()`——把应用带到前台（系统点击通知时通常已完成，失败可忽略）。
2. 若所属会话不是当前视图会话，调用 `uiWorkspace.openSession(sessionId)` 切换过去。
3. 若为交互通知，且 `kind` 为 `question` 或 `plan-review`、`callId` 是字符串，调用 `userQuestionPanels.reveal(sessionId, callId)` 重新打开可作答面板。
4. 关闭这条通知。

`uiWorkspace`、`userQuestionPanels` 都是可选能力：缺失时跳过对应步骤，通知本身仍可点击并关闭。

### 3.6 安静规则

只有在「看着会话也看不到事件」时才提醒；交互与完成通知共用同一套判定：

| 窗口状态 | 事件所属会话 | 结果 |
|---|---|---|
| 前台且聚焦 | 当前正在看的会话 | **不通知**（面板或结果就在眼前） |
| 前台且聚焦 | 别的会话 | 通知 |
| 后台（切到别的 App） | 任意会话 | 通知 |
| 最小化 / 页面不可见 | 任意会话 | 通知 |
| 无法读取窗口状态（异常） | 任意会话 | 通知（宁多勿漏） |

**调试开关**：需要验证通知链路时，在页面控制台设 `window.__DSH_MACOS_NOTIFY_ALWAYS__ = true`，再重载插件（插件页关开一次）或刷新窗口。开关只在模块加载时读取一次，仅跳过安静规则，权限与构造检查仍然生效。

## 4. 通知文案规格

### 4.1 结构

| 部分 | 内容 | 上限 |
|---|---|---|
| 标题 | 按 `kind` 取固定文案；完成通知用完成标题 | 60 字符（超长截断加 `…`） |
| 正文第一行 | 一句话说明在等什么，或说明本轮已结束 | 180 字符 |
| 正文第二行 | `会话：<标题>` | 会话标题 60 字符 |

正文两行用换行连接，整体不再二次截断。

### 4.2 模板与示例

| 场景 | 正文示例 |
|---|---|
| 授权（带原因） | `Bash：write outside workspace` |
| 授权（无原因） | `Bash 请求越权执行` |
| 授权（工具名缺失） | `有工具：…` / `有工具 请求越权执行` |
| 单个提问 | `要保留旧的导出函数吗？` |
| 多个提问 | `先改文案还是先改逻辑？（共 2 个问题）` |
| 计划审批 | `计划：扩展通知覆盖全部待处理交互` |
| 未知领域 | `有操作需要你处理` |
| 会话完成 | `本轮已结束，点击查看结果` |
| 第二行 | `会话：检查依赖` |

补充规则：

- 授权原因优先取 `displayReason`（经 `ctx.locale.resolveText` 解析），否则取 `reason`；都为空时用「请求越权执行」模板。
- 没有工具名时用「有工具」占位；没有问题时用「DSH 有一个问题要问你」占位。
- 计划审批标题取自计划 Markdown（见 4.3）；取不到时退回问题原文，再退回占位文案。
- 完成通知正文固定为「本轮已结束，点击查看结果」，不生成模型输出摘要。

### 4.3 计划标题提取

按计划 Markdown 的文本内容取标题，优先级从上到下：

1. 第一个 ATX 标题（`#` ~ `######`，最多 3 个前导空格），去掉行内 `*`、`_`、反引号后截断到 60 字符。
2. 没有标题时取第一条真实正文行：跳过空行、水平分隔线（`---` / `***` / `___`）、以三个反引号开头的代码围栏行，并去掉行首的引用或列表标记。
3. 都取不到时使用该问题的正文；仍为空则用占位文案。

### 4.4 归一化与语言

- 所有文案先折叠连续空白为单个空格，再 `trim`；超过上限时保留前 `limit - 1` 个字符并追加 `…`；非字符串输入一律视为空字符串。
- 文案注册在插件自己的 locale 命名空间 `dsh-macos-notify`，随 DSH 语言设置切换（简体中文 / English），代码里不硬编码可见文案。

## 5. 系统集成与权限

### 5.1 桌面端与浏览器

- 通知由渲染进程通过标准 Web Notification API 发出，由 DSH 桌面应用（Electron / Chromium）转成 macOS 通知；归属 **DeepSeek Harness**，带应用图标。
- 桌面端权限是应用级的：插件初始化时若发现 `permission === 'default'` 会主动 `requestPermission()`；没有用户手势时部分环境会保持待定，此时不通知，需要在系统或站点设置里手动允许。系统路径：**系统设置 → 通知 → DeepSeek Harness**。
- 通过 `dsh web` 访问时由浏览器发通知，需要允许该站点的通知权限；浏览器已允许但系统不弹时，检查 **系统设置 → 通知 → 浏览器** 与站点权限。

### 5.2 权限缺失与降级

- 权限不是 `granted` 时完全不创建通知（交互与完成都一样），不重试、不弹错误。
- `Notification` 缺失、构造抛错、点击回调中的会话切换失败，都被捕获并忽略。
- 通知链路全挂也不影响 DSH 的授权 / 提问 / 计划流程，会话完成也不会被影响。

## 6. 安装、升级与卸载

### 6.1 bundle 组成

| 层 | 文件 | 职责 |
|---|---|---|
| 清单 | `package.json` | 声明 `dsh.bundle.patch`、`dsh.client`（platform `web`，`immediately: true`，inject `@deepseek-ai/dsh-client-ui-session` 与 `@deepseek-ai/dsh-client-ui-session-status`），以及 `engines.dsh` |
| Bundle 补丁 | `cordis.patch.yml` | 在 Loader 中插入一行：`id: macos-notify`、`name: dsh-macos-notify` |
| Host 半 | `index.js` | 空实现 `apply()`，只为让 Loader 行有效；所有逻辑在 Client 半 |
| Client 半 | `client.js` | 订阅待处理交互与运行状态、决定是否通知、构造通知、处理点击与关闭 |
| 其余 | `locale/`、`icon.svg`、`scripts/smoke-test.mjs`、`README.md` | 插件页文案与图标、无 DSH 的决策逻辑烟测、用户手册 |

无构建步骤：`client.js` 本身就是运行产物。

### 6.2 安装

安装步骤见 README 的「安装」一节。安装后必须**刷新窗口**：桌面端从 profile 软链读取 `client.js`，不刷新会继续运行旧版。

### 6.3 生效、重载与升级

- 修改 `client.js` 后刷新窗口；插件页里关开一次插件开关也会重新加载。
- 调试开关在模块加载时读取一次，所以要先设开关、再重载。
- 升级只需替换文件并刷新窗口，没有构建产物需要重新生成；版本号规则见 6.5。

### 6.4 卸载

- 插件页 **Remove**：从 profile 的 bundle 列表与依赖中移除，刷新窗口后彻底消失。
- 只关闭插件开关：立即停止通知，保留安装。
- 卸载或禁用时，插件会退订事件并关闭已弹出的通知，不留残留。

### 6.5 版本号与发版

`package.json` 的 `version` 是唯一版本源；git tag 命名为 `v<version>`，第 11 节「版本记录」按版本追加变更摘要。

| 改动 | 升位 | 示例 |
|---|---|---|
| 修复、文案、裁剪、权限降级 | PATCH `0.2.1` | 通知不关闭、正文格式错、权限处理 |
| 新功能、新覆盖、新开关 | MINOR `0.3.0` | 覆盖新的 `kind`、增加完成通知、增加通知字段 |
| 破坏性变更、抬高最低 DSH 版本 | MAJOR `1.0.0` | 删除配置键、改点击语义 |

0.x 阶段 MINOR 是功能里程碑、PATCH 只修不破；`1.0.0` 之后严格按 SemVer。插件版本与 DSH 版本分开：依赖较新 DSH API 时用 `engines.dsh` 声明最低版本，每次抬高下限至少算一次 MINOR。

本地以 `link:` 安装时版本号只作标识，改文件刷新即生效；以 registry 分发时才需要升版本（当前 `private: true` 会阻止 `npm publish`）。提交、推送、发版与创建 Release 的执行规则见仓库根目录 [AGENTS.md](../AGENTS.md)。

## 7. 兼容性与已知限制

| 限制 | 说明 | 影响与应对 |
|---|---|---|
| 最低 DSH 版本 | `engines.dsh` 为 `^0.2.3-alpha.2`：从 `0.2.2-rc.2` 之后的版本起，`ctx.uiSession.sessionStatus` 是独立服务，读取它的插件必须注入该服务 | 更旧的 DSH 在安装 / 启动检查时以 `incompatible-version` 拒绝加载；升级 DSH 后刷新窗口 |
| Web Notification 能力边界 | 不是 `NSUserNotification` / `UNUserNotificationCenter` | 不支持通知内自定义按钮与通知中心的持久操作；提示音与横幅样式由系统设置决定 |
| 计划审批依赖 DSH 投影 | 插件不自己判断「这是不是计划审批」 | DSH 未识别为 `plan-review`（单个问题、带 `detail`、选项不超过 2 个且 `approve` 命中某选项）时按 `question` 处理 |
| 完成语义只看运行状态 | `running` 由 `true` 变 `false` 就算完成，不区分正常结束、失败与用户取消 | 失败或取消时也可能弹「DSH 会话已完成」；把它当作「agent 已空闲」而不是成功保证 |
| 完成通知不覆盖子会话 | `origin === 'subagent'` 的会话完成时不通知 | 主会话结束时会单独提醒，避免一次任务弹出一串完成通知 |
| 重载期间的完成会丢失 | 插件只在加载后观测 `running` 边沿 | 页面刷新或插件重载时刚好完成的轮次不会补弹 |
| 可选能力缺失 | `uiWorkspace` 缺失时无法切会话；`userQuestionPanels` 缺失时无法重开面板（由 `ui-user-questions` 提供） | 点击仍会聚焦应用并关闭通知 |
| 本地安装 | `private: true`，以 `link:` 目录安装 | 适合本地开发 / 自用；分发给他人需发布或按 bundle 规范打包 |

## 8. 测试与验收

测试分两层：**自动化烟测**证明「插件做出了正确的通知决策」，**真机验收**证明「macOS 真的弹了、点击真的回来了」。两者不能互相替代。

### 8.1 自动化烟测

```bash
node --check client.js
node scripts/smoke-test.mjs
```

烟测把 `client.js` 加载进 Node 的 VM 沙箱，用假的 Cordis 上下文、假的 `document`、假的通知实现与可变的会话状态，覆盖 **31 项断言**：安静规则 8、问答 / 计划 / 未知领域 7、always 调试开关 2、装入断言 1、会话完成 13。它不接触操作系统通知，也不验证 Electron 集成；断言清单以 `scripts/smoke-test.mjs` 为准。

### 8.2 真机验收

前置条件：插件已安装并刷新过窗口；macOS 通知权限已授予（见第 5 节）。四条用例约需 6 分钟。

#### 用例 A：授权（`approval`）

触发一次工作区外写入。命令自带清理，失败时手动删掉 `$HOME/dsh-notify-test`：

```bash
mkdir -p "$HOME/dsh-notify-test" && rmdir "$HOME/dsh-notify-test"
```

1. 把窗口切到别的 App（或最小化）。
2. 让 DSH 执行上面的命令，应弹出：标题 `DSH 等待你的授权`，正文 `Bash：<原因>`（没有原因时是 `Bash 请求越权执行`），第二行 `会话：<标题>`。
3. 点击通知：回到本会话并看到授权面板；点「允许」。
4. 通过标准：授权处理后通知自动消失，通知中心不留条目。

#### 用例 B：提问（`question`）

1. 让 DSH 向你提问（例如「先问我一个问题再继续」）。
2. 切到后台，应弹出：标题 `DSH 等待你的回答`，正文是问题原文；一次提交多个问题时追加「（共 N 个问题）」。
3. 点击通知：回到本会话，被收起的提问面板会重新打开（`userQuestionPanels.reveal()`）。
4. 作答后通知自动消失。

#### 用例 C：计划审批（`plan-review`）

1. 输入 `/plan` 进入计划模式，输入区右侧出现蓝色 **Plan** 芯片。
2. 发一个要规划的任务，等 agent 提交计划。
3. 切到后台，应弹出：标题 `DSH 等待你审批计划`，正文 `计划：<计划 Markdown 的一级标题>`。
4. 点击通知：回到会话并打开计划；批准或拒绝后通知消失。
5. 收尾：点 Plan 芯片或输入 `/plan off` 退出——选「拒绝」不会自动退出计划模式。

#### 用例 D：完成（`running` 边沿）

1. 给 DSH 一个不会触发授权或提问的任务（例如「列出当前目录并总结」）。
2. 在任务运行中把窗口切到别的 App（或最小化）。
3. 等任务跑完，应弹出：标题 `DSH 会话已完成`，正文 `本轮已结束，点击查看结果`，第二行 `会话：<标题>`。
4. 点击通知：回到本会话并看到结果；不点通知而直接发送下一条消息时，旧完成通知会自动收起。
5. 对照检查：前台正看着该会话时跑完不弹；跑完同时带提问或计划审批时只弹交互通知；子会话跑完不单独弹。

### 8.3 排障

| 现象 | 先查 |
|---|---|
| 完全没弹 | 是否刷新加载了新版；通知权限（应用级 / 站点级）；当时是否正看着事件所属的会话；插件开关是否关闭 |
| 完成后没弹 | 任务是否真的进入过运行状态（`running: true`）；当时是否正看着该会话；结束瞬间是否带着待处理交互；是否为子会话；是否在页面刷新 / 插件重载期间完成 |
| 完成通知说「已完成」但其实失败了 | 完成语义只来自 `running` 边沿，不区分成功、失败与取消；以会话里的实际结果为准 |
| 标题是「DSH 等待你的响应」 | 该请求的 `kind` 不属于 `approval` / `question` / `plan-review`，走通用兜底，属预期 |
| `plan-review` 被当成提问 | 该请求未被 DSH 识别为计划审批：需单个问题、带 `detail`、选项不超过 2 个且 `approve` 命中某个选项 |
| 点击后没回到会话，或没有面板 | `uiWorkspace.openSession()` / `userQuestionPanels` 是否可用；会话是否已归档或删除 |
| 有多个请求但看起来只有一条 | 是否同一个 `pending.key`（同一 tag，系统会合并）；macOS 也可能把同一应用的通知折叠分组，展开分组查看 |

## 9. 技术设计

### 9.1 数据流

```text
uiSession.sessionStatus            （Host 投影：待处理交互 + 运行状态；需 inject 的独立服务）
        │  Map<sessionId, { pendingInteraction, running }>
        ▼
   reconcile()
        │
        ├─ trackRunning()  ── running: true → false 且无阻塞交互 ──► showFinished()
        │                       │                                        │
        │                       └─ running: true ──► dismissFinished()    └─ finished.take/replace
        │
        └─ pending 过滤已结算 / 去重 ──► show() / dismiss()
        │
        ├─ 安静规则（visibilityState / hasFocus / 当前会话）
        ├─ 文案（kind / 完成 → 模板 → 裁剪）
        └─ new Notification(title, { body, tag })

   点击 / 请求消失 / 下一轮开始 / 会话离开快照 / 插件下线
        └─► focusSession() / reveal() / close()
                ├─ window.focus()
                ├─ uiWorkspace.openSession()
                └─ userQuestionPanels.reveal()（仅提问与计划审批）
```

### 9.2 关键取舍

**为什么只读观察快照，而不是拦 waterfall。**
客户端 waterfall 由各自的 UI 包注册并持有到用户作答，后注册的监听器拿不到请求；即使拿到，也很容易不小心「消费」掉决策。`sessionStatus` 是只读发布面，观察它不会改变任何决策，也不会与面板抢时序。

**为什么按 `kind` 分发，而不是特判授权。**
`sessionStatus` 已经把三类交互统一投影成 `pendingInteraction`；按 `kind` 取文案既能覆盖提问与计划审批，也让未来新增领域自动获得通知。

**为什么安静规则同时看 `visibilityState` 与 `hasFocus()`。**
只看其中之一会漏掉「窗口可见但没聚焦」或「切到别的 App」这类情况；两者结合才能覆盖「看着会话也看不到事件」的全部状态。

**为什么完成也读 `sessionStatus`，而不是监听 Host 事件。**
`sessionStatus` 已把运行状态事件与会话目录基线合并成每会话一条快照，和交互投影在同一张 Map 上；读它既不需要引入 `remote` 依赖，也保证「完成」和「等待」看到同一时刻的状态。

**为什么必须注入 `uiSession.sessionStatus`。**
从 `0.2.2-rc.2` 之后，会话状态表是独立的 Cordis 服务。写进 `inject` 后，Cordis 会等该服务就绪再执行 `apply`，服务卸载或热重载时插件随之卸载并由 `ctx.effect` 清理；改用 `ctx.get()` 会绕过这条生命周期，留下指向已卸载状态表的订阅。

**为什么不用 DSH 自带的 `completionUnread`。**
它是会话目录的「未读完成」标记，主视图会话会被自动确认清除；窗口在后台、用户正停在当前会话时不会留下标记，正好漏掉最需要提醒的情况。插件因此自己记录 `running` 边沿，再叠加同一套安静规则。

### 9.3 状态与容错

- 交互通知保存为 `Map<pending.key, { sessionId, pending, notification }>`；完成通知保存为 `Map<sessionId, Notification>`；另有一张 `Map<sessionId, boolean>` 记录上一次观测到的 `running`。
- 对账是幂等的：只补缺、只删多；完成只认 `true → false` 边沿，重复快照不会重复弹。
- 所有跨包调用（`locale.resolveText`、`sessions.list`、`uiSession.current`、`openSession`、`panel.reveal`）都包在 `try/catch` 中；`close()` 失败（系统已收起）也被忽略；插件结束时（`ctx.effect` 清理）退订并关闭全部通知。
