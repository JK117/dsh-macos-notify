# dsh-macos-notify 产品文档

> 版本：0.2.0 · 平台：macOS 桌面端 / `dsh web` 浏览器 · 状态：已实现并通过真机验证（2026-11-06）
>
> 定位：README 面向「装好就能用」的使用者；本文面向产品、测试与维护，覆盖完整规格、边界条件、验收方法与设计依据。改行为时先更新本文规格，再改代码与烟测断言。

---

## 0. 一页纸摘要

| 项目 | 内容 |
|---|---|
| 一句话定位 | 把 DSH 里「等你响应」的阻塞交互镜像为 macOS 系统通知。 |
| 目标用户 | 常把 DSH 放后台、同时开多个会话、容易错过授权 / 提问 / 计划审批的人。 |
| 核心问题 | 阻塞交互只存在于对话面板中。窗口在后台、最小化，或请求属于别的会话时，用户不知道 agent 已经停下等待。 |
| 核心体验 | 只在「看不到面板」时弹一条两行通知；点击回到发起请求的会话，提问与计划审批自动重开作答面板。 |
| 覆盖交互 | 授权（`approval`）、提问（`question`）、计划审批（`plan-review`），以及未来任何待处理交互的通用兜底。 |
| 明确不做 | 不改交互决策、不拦 waterfall、不提供通知内快捷按钮、不做声音或免打扰策略、不做非 macOS 的专门适配。 |
| 关键取舍 | 只读观察 `uiSession.sessionStatus`；窗口在前台且正看着请求会话时保持安静。 |
| 最大限制 | 通知由渲染进程发出：页面关闭时没有通知；基于 Web Notification，而非原生通知 API。 |

## 1. 背景与目标

### 1.1 三个缺口

DSH 的所有阻塞交互——授权、提问、计划审批——都以对话内面板呈现。面板本身设计得很好，但把「需要响应」这件事锁在了窗口里：

1. **窗口不在前台**：切到别的 App 或最小化后，面板不可见，agent 一直停在那里等。
2. **请求属于别的会话**：多会话并行时，你眼前的会话没有异常，另开一个会话的请求可能已经等了很久。
3. **回到窗口才发现**：等你想起来切回 DSH，可能已经浪费了几分钟。

系统通知是唯一跨应用可见的提醒通道；而 macOS 上真正「属于 DSH」的通知，应该由 DSH 自己发出，而不是借助终端或脚本进程。

### 1.2 产品目标

| 目标 | 含义 | 落地方式 |
|---|---|---|
| 不遗漏 | 所有阻塞交互都能提醒 | 订阅待处理交互快照，覆盖全部 `kind`，未知领域走通用兜底 |
| 不打扰 | 看得见面板时不弹 | 前台 + 当前会话 + 已聚焦 → 静默 |
| 可定位 | 从通知回到来源 | 点击切会话；提问 / 计划审批重开面板 |
| 无副作用 | 不改变交互语义 | 只读观察发布面，不消费、不重排、不改写决策 |
| 可降级 | 权限或 API 缺失不影响主流程 | 所有外部调用容错，失败静默 |

### 1.3 非目标

- 不做通知内的「允许 / 拒绝 / 回答」快捷操作。
- 不做通知声音、免打扰时段、通知优先级策略。
- 不替代对话内面板，也不改变面板的展开与收起逻辑。
- 不为 Linux / Windows 做平台适配（实现本身基于 Web 标准，可随之工作，但只按 macOS 验收）。
- 不做「离开页面后仍能通知」的后台常驻能力。

## 2. 用户与场景

### 2.1 用户画像

| 画像 | 特征 | 核心诉求 |
|---|---|---|
| 后台长任务用户 | 让 agent 跑构建、改文件，自己切去浏览器或编辑器 | 被阻塞时立刻知道 |
| 多会话并行用户 | 同时开几个会话，频繁切换 | 知道是「哪个会话」在等 |
| 计划模式用户 | 习惯先出方案、再批准实施 | 计划提交后能第一时间审批 |
| 浏览器 / Web 用户 | 通过 `dsh web` 使用，不一定用桌面端 | 同样的提醒，权限路径清楚 |

### 2.2 典型场景

1. **后台跑任务**：切去看日志，agent 请求写入工作区外文件 → 系统通知，点击回来点「允许」。
2. **多会话**：正在改前端，另一个会话的提问已经等了 3 分钟 → 通知里直接写会话名。
3. **计划审批**：提交方案后去倒咖啡 → 通知显示 `计划：<方案标题>`，回来批准。
4. **误触通知**：只想看看是哪个会话，不想切走 → 看通知内容即可，点击才切换。

### 2.3 用户故事

| ID | 用户故事 | 优先级 | 验收要点 |
|---|---|---|---|
| US-01 | 作为后台用户，窗口不在前台时我能收到通知。 | P0 | 失焦或不可见 → 通知 |
| US-02 | 作为多会话用户，我能从通知看出是哪个会话在等。 | P0 | 第二行 `会话：<标题>` |
| US-03 | 作为被阻塞的用户，我能一眼看出在等什么。 | P0 | 正文含工具与原因 / 问题原文 / 计划标题 |
| US-04 | 作为只想确认状态的用户，我不想点通知就切走。 | P1 | 只有点击才切换会话 |
| US-05 | 作为问答复用的用户，点击后我能直接作答。 | P1 | 重新打开提问面板 |
| US-06 | 作为已经处理完的用户，我不想被残留通知打扰。 | P0 | 请求解决后通知关闭 |
| US-07 | 作为权限被拒的用户，我希望 DSH 的其他功能照常可用。 | P0 | 静默降级，不报错 |

## 3. 功能规格

### 3.1 交互覆盖矩阵

插件按 `pendingInteraction.kind` 分发，不针对某一种交互写特判：

| `kind` | 典型来源 | 标题 | 正文（第一行） | 点击行为 |
|---|---|---|---|---|
| `approval` | 工具申请越权执行 | `DSH 等待你的授权` | `工具：原因`；无原因时 `工具 请求越权执行` | 切到会话，不额外重开面板 |
| `question` | `ask_user_question` 提问 | `DSH 等待你的回答` | 第一个问题的原文；多个问题时追加 `（共 N 个问题）` | 切到会话 + 重开作答面板 |
| `plan-review` | 计划模式提交方案 | `DSH 等待你审批计划` | `计划：<方案标题>`；取不到标题时退回问题原文 | 切到会话 + 重开作答面板 |
| 其他（未来新增） | 任何注册到待处理交互的领域 | `DSH 等待你的响应` | `有操作需要你处理` | 切到会话 |

正文第二行统一为 `会话：<会话标题>`；会话标题暂不可用时省略该行。

### 3.2 一次通知的判定流程

按顺序检查，任一步不通过就不创建通知：

1. **数据在**：`uiSession.sessionStatus` 快照中该会话有 `pendingInteraction`。
2. **未结算**：不存在 `review`（只读「查看回答」回放卡片），且 `answerable !== false`。
3. **可索引**：`pendingInteraction.key` 是字符串。
4. **能发**：`globalThis.Notification` 是构造函数，且 `Notification.permission === 'granted'`。
5. **该提醒**：通过安静规则（见 3.6）。
6. **构造成功**：`new Notification(title, { body, tag })` 不抛错。

### 3.3 静默、去重与关闭

- **同一请求只一条**：活动通知以 `pending.key` 为索引保存在内存 Map 中；已存在的 key 不会重复创建。
- **系统层合并**：`tag` 为 `dsh-macos-notify:<sessionId>:<pending.key>`。tag 相同的通知由 macOS 合并；不同请求 tag 不同，互不覆盖。
- **已结算不提醒**：`review` 卡片（回答回放）与 `answerable === false` 的授权既不创建通知，也会让同 key 的残留通知关闭。
- **请求消失即关闭**：每次快照变化后，所有「不在当前待处理集合里」的活动通知都会被 `close()`。
- **插件下线即清空**：禁用、卸载或热重载时退订 `sessionStatus`，并关闭全部活动通知。

### 3.4 点击行为

点击通知按以下顺序执行，每一步失败都不影响后续可用部分：

1. `window.focus()`——把应用带到前台（系统点击通知时通常已完成，失败可忽略）。
2. 若请求会话不是当前视图会话，调用 `uiWorkspace.openSession(sessionId)` 切换过去。
3. 若 `kind` 为 `question` 或 `plan-review`，且 `callId` 是字符串，调用 `userQuestionPanels.reveal(sessionId, callId)` 重新打开可作答面板。
4. 关闭这条通知。

`uiWorkspace`、`userQuestionPanels` 都是可选能力：缺失时跳过对应步骤，通知本身仍可点击并关闭。

### 3.5 生命周期

| 事件 | 行为 |
|---|---|
| 首次观测到未结算的待处理交互 | 创建通知并记入活动表 |
| 同一交互仍在等待 | 不重复创建 |
| 用户点击 | 聚焦 → 切会话 → 重开面板 → 关闭通知 |
| 用户作答 / 允许 / 拒绝 / 请求被撤回 | 下次快照对账时关闭并移除 |
| 通知权限被拒绝 | 不创建，静默 |
| 插件禁用、卸载、热重载 | 退订、关闭全部残留通知 |

### 3.6 安静规则

只有在「看着面板也看不到请求」时才提醒：

| 窗口状态 | 请求所属会话 | 结果 |
|---|---|---|
| 前台且聚焦 | 当前正在看的会话 | **不通知**（面板就在眼前） |
| 前台且聚焦 | 别的会话 | 通知 |
| 后台（切到别的 App） | 任意会话 | 通知 |
| 最小化 / 页面不可见 | 任意会话 | 通知 |
| 无法读取窗口状态（异常） | 任意会话 | 通知（宁多勿漏） |

**调试开关**：需要验证通知链路时，在页面控制台执行 `window.__DSH_MACOS_NOTIFY_ALWAYS__ = true`，然后重载插件（插件页关开一次）或刷新窗口。开关在模块加载时读取一次，只跳过安静规则；权限、构造失败等检查仍然生效。点击通知时若已在目标会话，不会重复切换。

## 4. 通知文案规格

### 4.1 结构

一条通知由三部分组成：

| 部分 | 内容 | 上限 |
|---|---|---|
| 标题 | 按 `kind` 取固定文案 | 60 字符（超长截断加 `…`） |
| 正文第一行 | 一句话说明在等什么 | 180 字符 |
| 正文第二行 | `会话：<标题>` | 会话标题 60 字符 |

正文两行用换行连接，整体不再二次截断。

### 4.2 模板与示例

| 场景 | 正文示例 |
|---|---|
| 授权（带原因） | `Bash：write outside workspace` |
| 授权（无原因） | `Bash 请求越权执行` |
| 授权（工具名缺失） | `有工具：…` / `有工具 请求越权执行` |
| 单个提问 | `要保留旧的导出函数吗？` |
| 多个提问 | `先改文案还是先改逻辑？（共 2 个问题）` |
| 计划审批 | `计划：扩展通知覆盖全部待处理交互` |
| 未知领域 | `有操作需要你处理` |
| 第二行 | `会话：检查依赖` |

补充规则：

- 授权原因优先取 `displayReason`（可能带本地化文本，先经 `ctx.locale.resolveText` 解析），否则取 `reason`；两者都为空时用「请求越权执行」模板。
- 没有工具名时用「有工具」占位；没有问题时用「DSH 有一个问题要问你」占位。
- 计划审批的标题取自计划 Markdown（见 4.3）；一个计划都取不到时退回该问题原文，再退回占位文案。

### 4.3 计划标题提取

按计划 Markdown 的文本内容取标题，优先级从上到下：

1. 第一个 ATX 标题（`#` ~ `######`，最多 3 个前导空格），去掉行内 `*`、`_`、反引号后截断到 60 字符。
2. 没有标题时，取第一条真实正文行：跳过空行、水平分隔线（`---` / `***` / `___`）、以三个反引号开头的代码围栏行，并去掉行首的引用或列表标记。
3. 都取不到时，使用该问题的正文；仍为空则用占位文案。

### 4.4 裁剪与归一化

- 所有文案先折叠连续空白为单个空格，再 `trim`。
- 超过上限时保留前 `limit - 1` 个字符并追加 `…`。
- 非字符串输入一律视为空字符串，不抛错。

### 4.5 语言与键集

- 文案字典注册在插件自己的 locale 命名空间 `dsh-macos-notify`，随 DSH 语言设置切换（简体中文 / English）。
- 中文词典是键集基准；英文词典必须与之键集完全一致，缺失会在烟测中直接失败。
- 标题、正文、会话行、占位词全部走字典，不在代码里硬编码可见文案。

## 5. 系统集成与权限

### 5.1 桌面端

- 通知由渲染进程通过标准 Web Notification API 发出，由 DSH 桌面应用（Electron / Chromium）转成 macOS 通知。
- 通知归属 **DeepSeek Harness**，带应用图标，而不是「脚本编辑器」之类的辅助进程。
- 权限是应用级的：插件初始化时若发现 `permission === 'default'` 会主动 `requestPermission()`。没有用户手势时，部分环境（尤其是浏览器）会把权限保持在待定，此时不会发出通知，需要在系统或站点设置里手动允许。
- 系统权限路径：**系统设置 → 通知 → DeepSeek Harness**。

### 5.2 纯浏览器访问

- 通过 `dsh web` 打开页面时，由浏览器发通知，需要允许该站点的通知权限。
- 若浏览器已允许但系统不弹，检查 **系统设置 → 通知 → 浏览器**，以及浏览器自身的站点权限。
- 页面必须保持打开：关闭标签页后通知链路随页面一起消失。

### 5.3 权限被拒绝或能力缺失

- 权限不是 `granted` 时完全不创建通知，不重试、不弹错误。
- `Notification` 缺失、构造抛错、点击回调中的会话切换失败，都被捕获并忽略。
- 插件永远不阻塞或改变交互面板本身：即使通知链路全挂，DSH 的授权 / 提问 / 计划流程照常。

## 6. 安装、升级与卸载

### 6.1 bundle 组成

| 层 | 文件 | 职责 |
|---|---|---|
| 清单 | `package.json` | 声明 `dsh.bundle.patch`、`dsh.client`（platform `web`，`immediately: true`，inject `@deepseek-ai/dsh-client-ui-session`） |
| Bundle 补丁 | `cordis.patch.yml` | 在 Loader 中插入一行：`id: macos-notify`、`name: dsh-macos-notify` |
| Host 半 | `index.js` | 空实现 `apply()`，只为让 Loader 行有效；所有逻辑在 Client 半 |
| Client 半 | `client.js` | 订阅待处理交互、决定是否通知、构造通知、处理点击与关闭 |
| 文案 | `locale/zh.json`、`locale/en.json` | 插件页卡片的标题与描述（不是通知文案） |
| 图标 | `icon.svg` | 插件页卡片图标 |
| 测试 | `scripts/smoke-test.mjs` | 无 DSH 的决策逻辑烟测 |
| 文档 | `README.md`、`docs/产品文档.md` | 用户手册 + 本文 |

无构建步骤：`client.js` 本身就是运行产物。

### 6.2 安装

1. 打开侧边栏「插件」页 → **Add plugin** → **Install a third-party plugin**。
2. 填入本目录的绝对路径。安装会把该目录以 `link:` 依赖写入 profile，并选中它的 bundle 层。
3. **刷新窗口**。桌面端从 profile 软链读取 `client.js`，不刷新会继续运行旧版。
4. 验证：把窗口切到后台，让 DSH 执行一个需要授权的操作（或向它提问一次），应看到系统通知。

### 6.3 生效、重载与升级

- 修改 `client.js` 后必须刷新窗口；插件页里关开一次插件开关也会重新加载。
- 调试开关在模块加载时读取一次，所以要先设置开关、再重载。
- 升级只需替换文件并刷新窗口，没有构建产物需要重新生成；需要区分版本时同步更新 `package.json` 的 `version`。

### 6.4 卸载

- 插件页 **Remove**：从 profile 的 bundle 列表与依赖中移除，刷新窗口后彻底消失。
- 只关闭插件开关：立即停止通知，保留安装。
- 卸载或禁用时，插件会退订事件并关闭已弹出的通知，不留残留。

## 7. 兼容性与已知限制

| 限制 | 说明 | 影响与应对 |
|---|---|---|
| 依赖页面在线 | 通知由渲染进程发出，页面完全关闭时没有通知 | 此时也没有可作答的 UI；如需离页面提醒，需要常驻进程，超出当前范围 |
| Web Notification 能力边界 | 不是 `NSUserNotification` / `UNUserNotificationCenter` | 不支持通知内自定义按钮、通知中心的持久操作；提示音与横幅样式由系统设置决定 |
| 仅 Web 客户端 | `dsh.client.platform: "web"` | 不影响 TUI / ACP 使用，但也不会为它们发通知 |
| 依赖 DSH 投影 `kind` | 插件不自己判断「这是不是计划审批」 | DSH 未识别为 `plan-review`（单个问题、带 `detail`、选项不超过 2 个且 `approve` 命中某选项）时会按 `question` 处理 |
| 会话标题来源 | 取 `sessions` 目录快照 | 目录尚未加载或标题为空时，省略第二行 |
| 可选能力缺失 | `uiWorkspace` 缺失时无法切会话；`userQuestionPanels` 缺失时无法重开面板（由 `ui-user-questions` 提供） | 点击仍会聚焦应用并关闭通知 |
| 本地安装 | `private: true`，以 `link:` 目录安装 | 适合本地开发/自用；分发给他人需发布或按 bundle 规范打包 |
| 系统通知设置 | 用户可能设为「不显示横幅」、勿扰模式或按应用关闭 | 插件无法感知，也不会绕过；排查时先看系统通知设置 |
| 同 tag 合并 | 同一请求重复上报时系统按 tag 合并 | 不同请求 tag 不同，不会互相覆盖 |

## 8. 测试与验收

测试分两层：**自动化烟测**证明「插件做出了正确的通知决策」，**真机验收**证明「macOS 真的弹了、点击真的回来了」。两者不能互相替代。

### 8.1 自动化烟测

```bash
node --check client.js
node scripts/smoke-test.mjs
```

### 8.3 真机验收

前置条件：

- 插件已安装，并且**刷新过窗口**（或关开过插件开关）。
- macOS 通知权限已授予（见第 5 节）。
- 按用例切换前后台：窗口在前台且正看着发起请求的会话时，按设计不弹。
- 三条用例约需 5 分钟。

#### 用例 A：授权（`approval`）

触发一次工作区外写入。命令自带清理，失败时手动删掉 `$HOME/dsh-notify-test`：

```bash
mkdir -p "$HOME/dsh-notify-test" && rmdir "$HOME/dsh-notify-test"
```

1. 先把窗口切到别的 App（或最小化）。
2. 让 DSH 执行上面的命令，应弹出：标题 `DSH 等待你的授权`，正文 `Bash：<原因>`（没有原因时是 `Bash 请求越权执行`），第二行 `会话：<标题>`。
3. 点击通知：回到本会话并看到授权面板；点「允许」。
4. 通过标准：授权处理后通知自动消失，通知中心不留条目。

#### 用例 B：提问（`question`）

1. 让 DSH 向你提问（例如「先问我一个问题再继续」）。
2. 切到后台，应弹出：标题 `DSH 等待你的回答`，正文是问题原文；一次提交多个问题时追加「（共 N 个问题）」。
3. 点击通知：回到本会话，并且**被收起的提问面板会重新打开**（`userQuestionPanels.reveal()`）。
4. 作答后通知自动消失。

#### 用例 C：计划审批（`plan-review`）

1. 输入 `/plan` 进入计划模式，输入区右侧出现蓝色 **Plan** 芯片。
2. 发一个要规划的任务，等 agent 提交计划。
3. 切到后台，应弹出：标题 `DSH 等待你审批计划`，正文 `计划：<计划 Markdown 的一级标题>`。
4. 点击通知：回到会话并打开计划；批准或拒绝后通知消失。
5. 收尾：点 Plan 芯片或输入 `/plan off` 退出——选「拒绝」不会自动退出计划模式。

2026-11-06，macOS 桌面端：

| 用例 | 结果 |
|---|---|
| 授权 | 通过：标题、正文、会话行正确；被处理后退场 |
| 提问 | 通过：标题、正文正确；点击回到会话并重开面板 |

### 8.5 排障

| 现象 | 先查 |
|---|---|
| 完全没弹 | 是否刷新加载了新版；通知权限（应用级 / 站点级）；当时是否正看着发起请求的会话（前台当前会话按设计不弹）；插件开关是否关闭 |
| 标题是「DSH 等待你的响应」 | 该请求的 `kind` 不属于 `approval` / `question` / `plan-review`，走通用兜底，属预期 |
| `plan-review` 被当成提问 | 该请求未被 DSH 识别为计划审批：需单个问题、带 `detail`、选项不超过 2 个且 `approve` 命中某个选项 |
| 点击后没回到会话 | `uiWorkspace.openSession()` 是否可用；会话是否已归档或删除 |
| 点击后没有提问面板或计划页 | `ctx.get('userQuestionPanels')` 不可用——该能力由 `ui-user-questions` 提供 |
| 有多个请求但看起来只有一条 | 是否同一个 `pending.key`（同一 tag，系统会合并）；macOS 也可能把同一应用的通知折叠分组，展开分组查看 |
| 页面关闭后没有通知 | 设计限制：通知由页面发出（见第 7 节） |
| 文案语言不对 | 是否跟随了 DSH 的语言设置；英文词典键集由烟测保证完整 |

## 9. 技术设计

### 9.1 数据流

```text
uiSession.sessionStatus            （Host 投影的待处理交互快照）
        │  Map<sessionId, { pendingInteraction }>
        ▼
   reconcile()  ── 过滤已结算 / 去重 ──►  show() / dismiss()
        │                                    │
        │                                    ├─ 安静规则（visibilityState / hasFocus / 当前会话）
        │                                    ├─ 文案（kind → 模板 → 裁剪）
        │                                    └─ new Notification(title, { body, tag })
        ▼
   点击 / 请求消失 / 插件下线  ──►  reveal() / close()
                                        │
                                        ├─ window.focus()
                                        ├─ uiWorkspace.openSession()
                                        └─ userQuestionPanels.reveal()
```

### 9.2 关键取舍

**为什么只读观察快照，而不是拦 waterfall。**
客户端 waterfall 由各自的 UI 包注册并持有到用户作答，后注册的监听器拿不到请求；即使拿到，也很容易不小心「消费」掉决策。`sessionStatus` 是只读发布面，观察它不会改变任何决策，也不会与面板抢时序。

**为什么按 `kind` 分发，而不是特判授权。**
`sessionStatus` 已经把三类交互统一投影成 `pendingInteraction`。按 `kind` 取文案既能覆盖提问与计划审批，也让未来新增领域自动获得通知（走通用文案），不需要改代码。

**为什么窗口在前台且正看着请求会话时不弹。**
面板已经覆盖输入区，再弹系统通知只是重复打扰。判断同时看 `document.visibilityState` 与 `document.hasFocus()`，覆盖「切到别的 App」「最小化」「窗口可见但没聚焦」三种情况。

**为什么通知里带会话名。**
后台会话的请求是最容易被忽略的情况。标题让用户判断值不值得立刻切过去；只看通知不会改变当前视图。

**为什么点击后才切换会话。**
只看通知不改变当前视图；点击是显式意图，才调用 `uiWorkspace.openSession()` 与 `userQuestionPanels.reveal()`。

### 9.3 状态与容错

- 活动通知保存为 `Map<pending.key, { sessionId, pending, notification }>`；对账是幂等的：只补缺、只删多。
- 每次快照变化、每次订阅回调都重新对账，不依赖增量的复杂事件。
- 所有跨包调用（`locale.resolveText`、`sessions.list`、`uiSession.current`、`openSession`、`panel.reveal`）都包在 `try/catch` 中：单点失败降级为「少一个细节」，不阻断通知链路。
- 通知的 `onclick` 在构造后绑定；`close()` 失败（系统已收起）也被忽略。
- 插件生命周期结束时（`ctx.effect` 清理）退订并关闭全部通知。

## 附录 B：术语

| 术语 | 含义 |
|---|---|
| bundle | DSH 的插件打包单位，可同时包含 Host 与 Client 两半，并通过 patch 插入 Loader 行 |
| Host 半 | 运行在 DSH 主进程 / Node 侧的插件代码；本插件为空实现 |
| Client 半 | 运行在渲染进程的代码，能访问 `document`、`window`、`Notification` |
| 待处理交互（pending interaction） | DSH 投影出的「阻塞 agent、等用户响应」的状态，含 `kind`、`key`、会话等内容 |
| `kind` | 交互领域：`approval`、`question`、`plan-review`，未来可能新增 |
| `tag` | Web Notification 的分组标识；相同 tag 的通知会被系统合并 |
| waterfall | Cordis 的事件式拦截链；插件刻意不参与，只读快照 |
| 安静规则 | 窗口在前台且正看着请求会话时不通知的判定 |
