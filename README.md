# dsh-macos-notify（macOS 交互通知）

DSH 需要你响应时，除了对话里的交互面板，再弹一条 **macOS 系统通知**。窗口在后台、最小化，或请求属于另一个 Session 时，你能立刻看到；点击通知回到对应会话，问题类请求还会顺手把作答面板重新打开。

![icon](icon.svg)

## 覆盖的交互

插件监听 DSH 的待处理交互（`ctx.uiSession.sessionStatus`），按 `pendingInteraction.kind` 分发：

| `kind` | 场景 | 通知标题 |
|---|---|---|
| `approval` | 工具请求越权执行，等你允许 / 拒绝 | `DSH 等待你的授权` |
| `question` | `ask_user_question` 提问，等你选择或作答 | `DSH 等待你的回答` |
| `plan-review` | 计划模式提交方案，等你批准 | `DSH 等待你审批计划` |
| 其它（未来新增） | 任何注册到待处理交互的领域 | `DSH 等待你的响应` |

已结算的只读「查看回答」卡片不会通知；提问回答完、授权被处理或请求被撤回后，通知自动关闭。

## 行为

- **只在「看不到面板」时打扰你**：
  - 窗口不在前台（切到别的 App、最小化）→ 通知；
  - 窗口在前台，但请求属于另一个 Session → 通知；
  - 窗口在前台且正看着发起请求的那个 Session → 不通知，面板已经在眼前。

> **调试开关**：需要验证通知链路时，在页面控制台先执行 `__DSH_MACOS_NOTIFY_ALWAYS__ = true`，再重载插件（或在插件页关开一次），就会变成「每次待处理请求都弹」。

- 通知内容：
  - 授权：标题 `DSH 等待你的授权`，正文 `工具：原因`，例如 `Bash：write outside workspace`；
  - 提问：标题 `DSH 等待你的回答`，正文是问题本身，多个问题时追加「（共 N 个问题）」；
  - 计划审批：标题 `DSH 等待你审批计划`，正文 `计划：<方案标题>`（取自计划 Markdown 的一级标题）；
  - 第二行统一是 `会话：<标题>`。
- 点击通知：把应用带到前台并切换到发起请求的 Session；提问 / 计划审批还会通过 `userQuestionPanels.reveal()` 重新打开可作答的面板。
- 文案跟随 DSH 的语言设置（简体中文 / English）。

通知由渲染进程的标准 Web Notification API 发出，桌面端会把它显示为归属「DeepSeek Harness」的系统通知（有应用图标），而不是「脚本编辑器」之类的辅助进程。

## 安装

这是一个 DSH bundle，Host 半为空实现，全部逻辑在 Client 半（`client.js`）。

1. 侧边栏「插件」页 → **Add plugin** → **Install a third-party plugin**，填入本目录的绝对路径。
2. 安装后刷新窗口。
3. 把窗口切到后台，再让 DSH 执行一个需要授权的操作（或向它提问一次），应该能看到系统通知。

卸载使用插件页的 Remove；关闭插件开关也会立即停止通知。

## 权限

- **桌面端**：通知权限由 DSH 桌面应用本身持有，首次弹通知时 macOS 可能询问一次「DeepSeek Harness 想要发送通知」，允许即可。
- **纯浏览器访问**（`dsh web` 后自己打开地址）：由浏览器发通知，需要在浏览器里允许该站点通知；若系统通知里找不到，检查「系统设置 → 通知 → 浏览器 / DeepSeek Harness」。
- 权限被拒绝时插件静默工作，不影响交互流程本身。

## 真机测试

自动化只能证明「插件决定发通知」，不能证明「系统真的弹了」。真机测试验证的是渲染进程 `Notification` 到通知中心这一跳，以及点击后的回跳。三条用例大约 5 分钟。

前置条件：

- 插件已安装，并且**刷新过窗口**——桌面端从 profile 软链读取 `client.js`，改完文件不刷新仍是旧版；插件页关开一次也可以。
- macOS 通知权限已授予（见上一节）。
- 测试时按用例切换前后台：窗口在前台且正看着发起请求的会话时，按设计不弹通知。

### 用例 A：授权（`approval`）

触发一次工作区外写入。命令自带清理，失败时手动删掉 `$HOME/dsh-notify-test`：

```bash
mkdir -p "$HOME/dsh-notify-test" && rmdir "$HOME/dsh-notify-test"
```

1. 先把窗口切到别的 App（或最小化）。
2. 让 DSH 执行上面的命令，应弹出：标题 `DSH 等待你的授权`，正文 `Bash：<原因>`（没有原因时是 `Bash 请求越权执行`），第二行 `会话：<标题>`。
3. 点击通知：回到本会话并看到授权面板；点「允许」。
4. 通过标准：授权处理后通知自动消失，通知中心不留条目。

### 用例 B：提问（`question`）

1. 让 DSH 向你提问（例如「先问我一个问题再继续」）。
2. 切到后台，应弹出：标题 `DSH 等待你的回答`，正文是问题原文；一次提交多个问题时追加「（共 N 个问题）」。
3. 点击通知：回到本会话，并且**被收起的提问面板会重新打开**（`userQuestionPanels.reveal()`）。
4. 作答后通知自动消失。

### 用例 C：计划审批（`plan-review`）

1. 输入 `/plan` 进入计划模式，输入区右侧出现蓝色 **Plan** 芯片。
2. 发一个要规划的任务，等 agent 提交计划。
3. 切到后台，应弹出：标题 `DSH 等待你审批计划`，正文 `计划：<计划 Markdown 的一级标题>`。
4. 点击通知：回到会话并打开计划；批准或拒绝后通知消失。
5. 收尾：点 Plan 芯片或输入 `/plan off` 退出——选「拒绝」不会自动退出计划模式。

### 弹不出通知时先查什么

| 现象 | 先查 |
|---|---|
| 完全没弹 | 是否刷新加载了新版；通知权限；当时是否正看着发起请求的会话（前台当前会话按设计不弹） |
| 标题是「DSH 等待你的响应」 | 该请求的 `kind` 不属于 `approval` / `question` / `plan-review`；`plan-review` 需要单个问题、带 `detail`、选项不超过 2 个且 `approve` 命中某个选项 |
| 点击后没回到会话 | `uiWorkspace.openSession()` 是否可用；会话是否已归档或删除 |
| 点击后没有提问面板或计划页 | `ctx.get('userQuestionPanels')` 不可用——该能力由 `ui-user-questions` 提供 |
| 连续触发只看到一条 | macOS 按 `tag` 合并同名通知，属预期 |

### 最近一次实测

2026-11-06，macOS 桌面端：

| 用例 | 结果 |
|---|---|
| 授权 | 通过：标题、正文、会话行正确；被处理后退场 |

## 已知限制

- 依赖 DSH 客户端在线：通知由渲染进程发出，页面完全关闭时不会有通知（此时也没有可作答的 UI）。
- 使用的是 Web Notification，而不是直接调用 `NSUserNotification` / `UNUserNotificationCenter`，因此不提供自定义通知按钮或通知中心的持久操作。
- 已知的待处理交互领域目前只有 `approval`、`question`（含 `plan-review`）；新增领域会自动走通用文案，不需要改代码，但也不会带上领域特定的细节。

## 设计说明

- **为什么不拦任何 waterfall**：客户端 waterfall 由各自的 UI 包先注册并一直持有到用户作答，后注册的监听器拿不到请求；即使拿到，也容易不小心「消费」掉决策。待处理交互快照是只读发布面，观察它不会改变任何决策。
- **为什么按 kind 分发而不是特判授权**：`sessionStatus` 已经把三类交互统一投影成 `pendingInteraction`，按 kind 取文案既能覆盖提问，也能让未来新增领域自动获得通知。
- **为什么通知里带 Session 名**：后台 Session 的请求是最容易被忽略的情况，标题能让用户判断值不值得立刻切过去。
- **为什么前台当前会话不弹**：面板已经覆盖输入区，再弹系统通知只会造成重复打扰。
- **点击后才切换会话**：只看通知不改变当前视图；点击是显式意图，才调用 `uiWorkspace.openSession()` 与 `userQuestionPanels.reveal()`。
